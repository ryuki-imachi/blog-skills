## 1. タイトル

### パターンA: カテゴリ括弧型（トラブルシュート・小ネタ）
```
# 【カテゴリ】〜が〜しない／〜したい
```
例:
- `# 【Claude Code】カスタムステータスラインがホームディレクトリだけで表示されない`
- `# 【macOS】音声認識アプリのためのテスト音声を用意する`
- `# 【Claude Code】/insights のレポートが上書きされないように逃がしておきたい`

### パターンB: 解説・調査系
```
# 〇〇とは？ ── 副題
```
例:
- `# AWSが提唱する「AI-DLC」とは？ ── AIファーストの開発ライフサイクルを理解する`

**避けたい**:
- 過度に煽る、過度な絵文字、SEOキーワード羅列タイトル

### 見出し（セクションタイトル）は体言止め

- ✅ `## 検証環境の作成` / `## マージリクエストの自動レビュー` / `### Webhook 通知だけは VPC の外`
- ❌ `## 検証環境を作成` / `## 〜を試してみる` / `### 〜は VPC の外を通る`（文章形・動詞止め）
- 「はじめに」「おわりに」などの定型と「〜について」は可（2026-07-05 本人指定）

## 2. 必須セクション構成

締めは全ジャンル共通で `## おわりに`。`## まとめ` は基本使わない
（published 93記事の実績は「おわりに」65本＝70% に対して「まとめ」9本＝10%。
2026-08-13 本人指示「基本まとめには書かない想定でいいよ」）。
チートシート的な表を置きたい場合は `## 〇〇早見表` のように内容に即した体言止めの見出しで
本文側に置き、締めは「おわりに」で振り返る。

### トラブルシュート系
```
## はじめに         （機能/状況の紹介、画像、遭遇した現象）
## 前提環境         （macOS/Claude Code/各種バージョン）
## 起きていた現象   （表で「OK/NG」など対比）
## 切り分けの過程   （仮説1, 仮説2, 仮説3 ... と順番に検証）
## 結局：〜         （真因）
## 対処
## おわりに         （振り返り、教訓）
```

### 実装/手順系
```
## はじめに         （背景、何を作るか）
## 動作環境
## 今回やりたいこと
## 簡単な事前調査   （他の選択肢の比較、不要なら省略可）
## 使用ツール       （各ツールに公式リンク）
## 手順             （###1, 2, 3, ... ステップごと）
## おわりに
```

### 解説系
```
## はじめに
## 〇〇とは何か      （一言要約 → 詳細）
## 従来との比較     （表）
## 〇〇の3つのフェーズなど
## 用語整理         （表）
## おわりに
```

### 調査・検証系
```
## はじめに           （疑問・引っかかったこと → 結論の先出し）
## 用語 / 仕組みの整理 （表や図で対応関係を示す）
## 前提環境           （バージョンを表で。軽い記事なら :::note でも可）
## 挙動の確認         （実際に動かした結果。エラーメッセージは実物のまま貼る）
## 検証結果           （表で OK/NG を対比）
## 〇〇早見表         （チートシート的な表。「まとめ」ではなく内容に即した体言止めの見出し）
## おわりに           （振り返り → 教訓 → 今後 → ありがとうございました）
```

※`published/AgentCore Runtime パブリックデプロイの認証確認.md` と
`AgentCore Runtime 命名の落とし穴` に共通の型として2026-08-13に抽出。

ドキュメントの記述と手元での挙動が食い違った場合は、公式の記述を blockquote で引用したうえで
手元での挙動を採用する旨を明記する（`AgentCore Runtime 命名の落とし穴` の36文字問題が該当）。

「実測」「実測値」という語は本人が好まないため、レビュー時の提案でも使わない

## 3. 文体ルール

### 必須
- **「です・ます」調**で統一
- **一人称は「私」**
- **末尾は「ありがとうございました。」** で締める（解説系では「同じような需要のある方の参考になれば幸いです。」を挟むこともある）

### 語り口の癖（残してOK / むしろ推奨）
- 「ふと〜してみたら」「言われてみれば」「〜のかなと思いました」など、断定を避ける柔らかい表現
- 「最初は〜と疑いました」「ところが〜でした」など、思考の流れを追体験させる書き方
- 取り消し線 `~~反省が見られずちょっとイラっとしたので~~不便なので` のような自虐ユーモア
- 顔文字（🤨）や `:::note warn` 内の独白（「この「ついで」が大変だと気づくのはもう少し後のお話」）
- 仕組みや分担の説明を「〜という構図です」「〜という分担です」「〜という順番です」と名詞で締めて一文でまとめる（2026-08-02 棚卸し記事より）

### 控えるべき
- 上から目線（「〜すべきです」「〜しなければなりません」）
- 過度なカジュアル（「めっちゃ」「ヤバい」など）
- 絵文字の連打
- 記事のゴール宣言（「この記事のゴールは、読み終わったら〜できる状態になることです」）や、扱う範囲の但し書き（「〜には踏み込みません」）。「はじめに」は「この記事では〜します」の一文で締める（2026-08-08 本人指摘「私普段こんなことかかない」）
- インラインの (1)(2)(3) 列挙。並べたいときは地の文で流すか箇条書きにする（2026-08-14 Copilot対応記事レビューで本人承認）

## 4. Qiita 固有マークアップの使いこなし

### URL は単独行で書く（リンクカード化）
```markdown
https://code.claude.com/docs/ja/statusline
```
（前後を空行で挟む。インラインリンクではなく単独行）

### API・コマンドには関連ドキュメントのリンクを添える

API・CLIコマンドを実行する箇所には、関連する公式ドキュメント（サービスのユーザーガイドやCLIリファレンス）へのリンクを単独行URLで添える（2026-07-21 本人指定「API実行時などに関連ドキュメントのリンクを貼る癖をつけてほしい」）。レビュー時、コマンド実行箇所に関連ドキュメントリンクが無ければ指摘する。

### 公式ドキュメント引用は blockquote
```markdown
> The status line command only runs if you've accepted ...
```
英語引用の場合は直後に「訳すと、〜とのことです」と日本語訳を添える。

### `:::note` ブロック
- `:::note` — 補足
- `:::note warn` — 注意・余談・落とし穴

### 金額表記（`$` 記号を使わない）
金額は `$` 記号ではなくドル表記で書く（例: 6.20ドル）。Qiitaは `$...$` を数式（TeX）として解釈するため、1文に `$` が2つあると間が数式化して崩れる。コードブロック内は数式解釈されないので `$` のままでよい（2026-08-02 本人指摘）。

### 画像
- `![image.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/...)` のQiita image store URLを使う
- スクショには代替テキストを `image.png` のままでも可（リュウキは細かく書いていない）

## 5. コード・コマンド

- 言語指定は必須（```bash, ```json, ```markdown）
- 長いコマンドはバックスラッシュで改行
- コマンドの引数は地の文で説明: 「`-ar 16000` はサンプリング周波数を 16kHz に変換します。」
- ファイルパスは `~/.claude/settings.json` のように code 表記
- 実行結果はコメントで `# 実行結果` と添えてから貼る
- コードブロックは実物（コマンド・出力・エラー・ディレクトリツリー）専用。概念や対応関係の説明を整形テキストのコードブロックで書かない（表か地の文にする。2026-08-14 Copilot対応記事レビューで本人承認）

## 7. ひらがな化リスト（リュウキ準拠）

| 推奨（ひらがな） | NG（漢字） |
|---|---|
| できる | 出来る |
| ください | 下さい |
| 〜のため | 〜の為 |
| いただく | 頂く |
| すべて | 全て |
| わかる | 分かる |
| よさそう | 良さそう |
| 〜してみる | 〜して見る |

### 日本語と英数字の間のスペース

- **英字との間には半角スペースを入れる**: ✅ `WASM が動く仕組み` / `Claude Code で開いて` / `C/C++ や Rust など`
- **数字との間には入れない**: ✅ `2026年8月時点` / `2段階に分かれます` / `70週目`　❌ `2026 年 8 月時点`

published 全66記事の実測に基づく（英字の境界はスペース有 3,265 / 無 1,285、数字の境界はスペース有 413 / 無 783）。
バージョン番号など英字と一体の数字（`WebAssembly 3.0 が公開`）は英字側の扱いでスペースを入れる。
※2026-08-08、レビュー時にこの傾向を取り違えて「スペースを全部削除」と誤指摘した事故を受けて明文化。

## 8. 「リュウキらしさ」を奪わないための注意

レビュー時、以下は **改善提案として出さない**：

- AgentCore のような定着した通称・略称を初出で正式名称（Amazon Bedrock AgentCore 等）に展開すること（本人が通称のままを好む。2026-07-23 指摘不採用より）
- MCP のような開発者に浸透した略語を初出で展開（Model Context Protocol 等）すること（2026-08-02 指摘不採用「言わなくてもわかる」より）
- 自虐ユーモア・取り消し線（個性なので残す）
- 「〜のかなと思いました」「〜してみました」のような柔らかい締め（断定形を強要しない）
- 「おまけ(自分語り)」のようなセクション挿入（読み手が好む）
- 末尾の「ありがとうございました。」（リュウキの定型）
- 過去の自分の記事への自然な参照リンク
- 振り返り・自問系の文章形見出し（「〜である必要はあったのか」等）は個性として残す（2026-08-08 指摘不採用より。体言止めルールの例外）

逆に、以下が **欠けている場合は指摘する**：

- 「はじめに」「前提環境」「おわりに」のいずれかが無い
- タイトルにカテゴリ括弧が無い（パターンB のような解説系を除く）
- 末尾の「ありがとうございました。」が無い
- 公式ドキュメントへのリンクカード（単独行URL）が一つも無い
- バージョン情報が「前提環境」セクションに書かれていない
