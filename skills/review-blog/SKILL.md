# 技術ブログレビュースキル

リュウキの Qiita 投稿前記事をレビューする。**リュウキ自身の過去記事スタイルとの整合性**を重視し、
個性を奪わずに品質を底上げする方向で改善提案を出す。

## レビュー手順

1. **対象ファイルを読む**: `$ARGUMENTS` のファイルを Read。引数が無ければユーザーに「レビュー対象のファイルパスを指定してください」と伝えて中止
2. **スタイルガイドを読む**: 必ず最初に `${user_config.style_file}` を読む。未設定・ファイルが無い場合は、[references/my-style.md](references/my-style.md) をひな形に自分の文体ルールを書いて `/plugin configure blog-skills@ryuki-blog-skills` で登録するよう案内して中止する
3. **過去記事を参照**: `${user_config.articles_dir}/published/` 配下から、レビュー対象と**ジャンルが近い**完成記事（5KB以上のmd）を Glob + Bash の `find ... -size +5k` で抽出し、2〜3本を Read
   - トラブルシュート系 → 「〜しない／〜できない／〜表示されない」を含むファイル名
   - 実装/手順系 → 「〜してみた／〜を作る／〜する」を含むファイル名
   - 解説系 → 「〜とは／〜について」を含むファイル名
   - ジャンル判定が難しい場合は、最新更新日時の上位3本を選ぶ
4. **観点別にチェック**: [criteria.md](criteria.md) の各観点 + my-style.md の整合性チェック
5. **技術的記述の確認**: 古い情報やバージョン依存があれば WebSearch で最新情報を確認
6. **改善提案を出力**: 後述の出力フォーマットに従う。指摘は必ず「機械的な修正（ユーザーの判断不要）」と「判断してほしい提案（ニュアンス・構成）」に分けて提示する
7. **スタイルガイド更新の提案（改善ループ）**: 次の2つを検出したら、my-style.md への追記を1行の形で提案する（承認されるまで勝手に書き換えない）
   - レビュー対象の記事に繰り返し現れるが、my-style.md に未記載の表現・構成の癖 → 「残したい個性」の候補
   - レビュー後の修正対応でユーザーが受け入れなかった指摘 → セクション8「改善提案として出さない」リストへの追記候補（セッションの終わりに提案する）

### 指摘の2層分類（メリハリの原則）

- **機械的な修正（ユーザーが考えなくていい）**: 誤字脱字、ひらがな化リスト違反などの表記揺れ、ライブラリの公式表記、リンクカード形式、裏取り済みの明確な事実誤り。ユーザーは「適用して」の一言でまとめて直せる形で提示する
- **判断してほしい提案（ユーザーが考えるところ）**: 語り口・ニュアンス、構成の組み替え、主張の強さ、個性に関わる表現。1件ずつ理由を添えて提示し、押し付けない

## レビュー観点

| 観点 | チェック内容 |
|------|-------------|
| 技術的正確性 | 情報が正しいか、最新か、コードは動くか、バージョン明記 |
| 構成・流れ | リュウキの定型構成（はじめに → 本文 → まとめ → ありがとうございました）に沿っているか |
| 文体・語り口 | です・ます調、一人称「私」、柔らかい表現が一貫しているか |
| 読みやすさ | 1文の長さ、専門用語の説明（初出時に展開）、見出しの粒度 |
| 表記揺れ | 公式表記（Claude Code, GitHub, Node.js, macOS等）、ひらがな化（できる/ください等） |
| Qiitaマークアップ | 単独行URLでのリンクカード、`:::note` ブロック、コードブロックの言語指定 |
| リュウキスタイル整合性 | 過去記事と比較して文体・構成が浮いていないか |

詳細は [criteria.md](criteria.md) を参照。汎用的な良い例・悪い例は [examples.md](examples.md) を参照。

## 対象外（指摘しない）

- **Qiitaタグ** — 投稿時に手で設定するので無視
- **SEO / バズ要素** — 検索流入狙いの煽りタイトルなどは提案しない
- **他人の記事との比較** — 参考にするのはリュウキ自身の過去記事のみ
- **リュウキの個性** — 自虐ユーモア、取り消し線、「〜のかなと思いました」など柔らかい締めは残す（詳細は my-style.md セクション8）

## 出力フォーマット（2系統に分割）

レビュー結果は **ターミナル要約** と **詳細レポート (.review.md)** の2系統で出力する。
ターミナルが冗長で読みにくい問題を解消するため、詳細はファイルに、要点だけターミナルに。

### 1. 詳細レポート: `<元ファイルパス>.review.md` を Write

下書きの隣にレポートを書き出す。例: `~/.../foo.md` のレビュー → `~/.../foo.review.md`。
内容はフル詳細（全優先度の指摘、修正サンプル、参考にした過去記事リスト、総合評価）：

**番号は全指摘で通し**にする（機械的な修正が #1〜#3 なら、判断してほしい提案は #4 から続ける）。
ユーザーが「4だけ適用して」のように番号だけで採否を伝えられるようにするため（2026-07-23リュウキ指示）。
2層の分類（機械的/判断）自体は維持する。

```markdown
# レビューレポート: <元ファイル名>

生成日時: YYYY-MM-DD HH:MM
レビュー対象: <絶対パス>

## 📊 総合評価
⭐⭐⭐⭐☆（4/5）

## 🎯 リュウキスタイル整合性
- 構成: ...
- 文体: ...
- 末尾: ...
- 参考にした過去記事: ...

## ✅ 良い点
- ...

## 🔧 機械的な修正（判断不要 — 「適用して」の一言でまとめて直せます）

| # | 種類 | 問題箇所 | 修正案 |
|---|------|---------|--------|
| 1 | 誤字脱字/表記揺れ/公式表記/リンク形式/事実誤り | 引用 | 修正案 |

## 💭 判断してほしい提案（ニュアンス・構成・語り口）

| # | 観点 | 問題箇所 | 提案 | 理由 | 優先度 |
|---|------|---------|------|------|--------|
| 4 | 語り口 | 引用 | 提案 | なぜそう思うか | 高/中/低 |

（#は🔧からの通し番号）

## 🌱 スタイルガイドへの追記候補
（あれば。記事に繰り返し現れる未記載の癖など、1行の形で）

## 📝 修正後のサンプル
（必要に応じて。過去記事との照合付き）
```

### 2. ターミナル出力（圧縮）

ターミナルには **高優先度の指摘のみ** + 件数サマリ + レポートパスだけを出す。
中・低優先度は表示せず、全件はレポートファイル参照に誘導する。

```
📝 レビュー完了: <元ファイル名>

⭐ 総合評価: ⭐⭐⭐⭐☆（4/5）

🔧 機械的な修正: N件（誤字 X / 表記揺れ Y / その他 Z）
   →「適用して」の一言でまとめて直せます（考えなくてOK）

💭 判断してほしい提案のうち高優先度（N件）:
4. [観点] 問題箇所の要約 → 提案の要約（理由）※番号は🔧からの通し
5. ...

🌱 スタイルガイドへの追記候補: あり/なし

📊 件数サマリ: 機械的 N件 / 判断系 高 N件・中 M件・低 L件
📄 詳細レポート: <絶対パス>.review.md

良い点・低優先度の指摘・修正サンプルはレポートを参照してください。
```

### 優先度の基準

- **高**: 技術的な誤り、読者の誤解を招く問題、リュウキスタイルから明確に外れる構成
- **中**: 構成・読みやすさの改善、表記揺れ
- **低**: 細かい表現の好み、Qiitaマークアップの最適化

### 高優先度が0件の場合

ターミナル出力は次のように簡潔に：

```
📝 レビュー完了: <元ファイル名>
⭐ 総合評価: ⭐⭐⭐⭐⭐（5/5）

🔥 高優先度の指摘なし。

📊 件数サマリ: 高 0件 / 中 M件 / 低 L件
📄 詳細レポート: <絶対パス>.review.md
```

## 使い方

```
/review-blog ~/Desktop/draft.md
```

過去記事は自動で `${user_config.articles_dir}/published/` から
ジャンルに応じて選定するため、引数は対象ファイルパスのみ。
